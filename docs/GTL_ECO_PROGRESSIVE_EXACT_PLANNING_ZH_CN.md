得到首个可执行方案之后，原整单预算不再停止剩余路线枚举。单个候选仍有独立计算预算，耗尽时保留“未知”并继续其他候选；路线枚举结束时，如仍有未完成候选，界面明确显示优化尚未完成。搜索完全结束后不重复计算同一组路线。

## 数量模型

扩展工作区已有的 `PlannerAmount` / `U128`，不另建数量类型或规划器。

| 层级 | 范围与行为 |
| --- | --- |
| long | 能放入有符号 long 的值走原生快速路径 |
| 双 long 128 位 | 两个 long 保存完整 128 位幅值，差额符号单独保存 |
| BigInteger | 幅值达到 2^128 后兜底，运算结果缩小时回到能容纳它的较小层级 |

这次重点修复数量类型之间的调用边界，而不是只扩大某一个求解器的局部变量：

- 非循环需求、联合路线、循环矩阵、启动需求追加、跨组件外部需求、种子和进口上限保持精确数量。
- 库存快照同时保留有限大库存与无界供给身份。有限数量超过 long 不会变成无限库存，也不会在下单时被统一拒绝。
- 循环解保留精确任务向量、完整紧凑见证、产出和缺料，不因超 long 返回无见证的范围错误。联合优化器不再因宽数量丢弃可行候选。
- 执行任务总数、重复圈数、接受的提前执行量、动态次数、种子所有权和输入预留使用精确账本。重载时通过除法跳过整圈，不按巨大的执行次数逐次回放。
- 多个组件对相同材料的预留精确求和，然后与整单已用库存合并，避免漏算，也不重复计费。
- 执行计划和运行进度的 NBT：long 范围仍写 long / long 数组，宽数量写十进制字符串；读取兼容旧 long 存档。
- 图表传输保留精确边数量、次数和种子。宽边不再被直接省略，渲染时才进行数量格式化。

AE2 的 `KeyCounter`、普通 CPU 计划字段和普通派发批次接口仍然接收 long。它们只接收兼容投影或经过约束的实际批次；这些值不再回流成为 ECO 内部计算和累计执行的权威数量。普通 CPU 的能力限制、真实缺料和未解决循环仍会阻止提交。

## 两条记录对应的优化

请求 13 的原请求数量为 50,000,000,000,000,000，原日志的全路线乐观供应上界为 6,495,827,157,729,750。这个上界不足结论与水累计用量超过 long 是两个问题。修复精确执行不能凭空补足资源。

对大数量且存在活跃循环的请求，在昂贵的组件规划前尝试有预算的全路线供应证明。只有确实证明上界不足才提前返回；未知则正常规划。提前返回明确说明未展开完整材料详单，不编造缺料数量。证明记录有限库存、限制每个产出上界的输入组及传播关系，始终将上界与可执行最大数量区别开。

请求 14 的主要成本是首选之后的备选搜索。原日志 attempts=38 包含首选，并未证明其他路线全部不可行。累计水用量超过 long 不再单独构成换路线或中断循环外部规划的理由；完整精确方案可以直接发布，剩余优化留在后台。

复用 `RouteQuantityProof.Prepared` 的请求内模型和分支缓存，限制单次分支证明为至多 25,000 个检查点 / 10 ms，全局数量传播为至多 200,000 个检查点 / 50 ms；它们还受父预算约束。超时返回未知，不作为不可行证明剪枝。日志聚合数量证明耗时、检查点、缓存命中、受限次数、活跃图构造耗时、候选规划耗时及实际改变的生产者。

循环失败缓存与外部需求缓存继续按实际需求、精确库存、无界身份、已占用资源和边界限制区分子问题。副产物、替代输入和需要同时偏离多个选择的路线仍由原路线搜索覆盖。
