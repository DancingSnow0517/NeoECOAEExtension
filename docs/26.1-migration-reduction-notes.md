## 2. 推荐做法：`git merge main` 进 26.1，而不是手工复制

两条分支共享历史，merge 和"复制代码"效果相同，但额外能做到：
- 只有 main 改过的文件 → 直接用 main 版（之后再做 API 迁移）；
- 只有 26.1 改过的文件 → 自动保留已移植好的版本；
- 两边都改过的 174 个文件 → 产生冲突，以 26.1 的 API 形态为基础，把 main 的逻辑改动补进去；
- 保留 blame 和历史，以后 main 再有修复时可以继续 merge 或 cherry-pick。

步骤：
1. 从 `26.1` 切出 `port/26.1.2-sync` 分支，执行 `git merge main --no-commit`。
2. 冲突处理原则：**API 写法取 26.1，业务逻辑取 main**。`build.gradle`、`gradle.properties`、`neoforge.mods.toml` 以 26.1 为准，再按第 4 节手工补依赖。
3. `src/generated/resources` 冲突一律以 26.1 为准，最后用 `runData` 重新生成。
4. 先提交一个"merge（尚不能编译）"的提交，后续按模块逐个提交修复，便于 review。

## 5. 执行顺序（每步都应能编译，然后提交）

0. （已完成）本文即移植计划。
