# ECO 规划性能优化与 1.21.1 同步记录

日期：2026-10-25。适用于本次修改后的 Forge 1.20.1 与 NeoForge 1.21.1 工程。

## 现场问题与优化范围

现场请求为 `gtladditions:wireless_energy_network_input_terminal`，数量 `1000000000`。
旧 ECO 计算约两分钟后返回 `CYCLE_UNRESOLVED`。规划调用栈中，98.79% 的样本涉及备选路线搜索，
90.37% 涉及待满足需求遍历，83.62% 涉及流体键比较。这些调用链相互嵌套，比例不能相加。
同期整个游戏进程的 GC 暂停合计 322.805 ms。

GTL 的 GRAPH 引擎在后续同目标、同数量请求中记录了 334.2981、272.7910、355.4711 ms 的总耗时，
均为 `cache_hit=true`，结果为 `MISSING_SEED`。两边的结果状态和材料报告仍需对齐；这些数据用于定位响应延迟，
不能证明两个引擎已经计算出等价且可执行的计划。

## 已实现的改动

1. **按完整 AEKey 索引待满足需求。**
   `MaterialProvenance` 为每个完整物料键维护注册顺序和精确剩余总量。
   `pendingAmount` 直接查总量，`allocatePending` 只访问该物料仍未完成的需求，完成后移出待分配队列。
   组件/NBT 匹配继续使用 AEKey 原有的相等及哈希语义；不同但相等的键也能命中索引。
   复制、部分合并、回滚和目标转循环边界时同步维护索引。

2. **副产物信用预检后提交。**
   消费信用前先检查完整可用量、需求余额和物料来源，随后提交信用扣减及实际分配。
   无法满足的请求在修改前失败，避免每次信用消费复制、替换整份需求账本。
   来源顺序、未消耗信用和实际消费者的归属保持原有约定。

3. **在备选搜索前做保守数量上界证明。**
   `RouteQuantityProof` 将未知上界视为无穷大，从库存及全部模式传播物料数量上界。
   每条模式独立获得完整的乐观上游供给，忽略模式间竞争和执行顺序，并额外计入未公布的副产物。
   只有目标数量上界仍小于请求时，才跳过后续路线枚举，记录 `ROUTE_QUANTITY_BOUND`，保留已完成路线的完整材料报告。
   可增长循环、可复用返还物、创造/发射供应保持乐观上界。
   动态或组件忽略输入、不完整模式契约，以及达到本地 65536 次传播上限时均放弃该证明，继续原有求解流程。
   取消和会话预算通过检查点传播。

4. **复用循环外部供料的纯结构。**
   `ExternalDemandPlanner` 在同一次请求内缓存过滤后的网络、路线和 SCC 分析结果。
   键包含原网络身份、循环成员、被排除的物理模式和供料目标；网络改变会清空缓存。
   最多保留 16 项，总结构权重最多 50000，未完成的路线分析不进入缓存。
   数量、库存、预留和创造供应变化仍触发对应的数值求解，不跨订单复用库存结果。

这些优化默认生效。当前规划会话耗时配置保持原值，性能改善来自索引、预检、证明和结构复用。

## 旧源码与新源码的账本基准

使用同一 JVM 中的旧版原始源码与新实现，先预热 3 次，再取 5 轮耗时的中位数。
注册、Minecraft 测试启动和最终完整性检查均在计时区间外。
每轮结束均检查实际分配的完整性。

| 场景 | 规模 | 1.20.1 旧 / 新 ms | 1.21.1 旧 / 新 ms | 键比较次数：旧 → 新 |
|---|---:|---:|---:|---:|
| 不同物料的查询与分配 | 4000 种 | 265.6588 / 1.9321 | 225.3186 / 1.4228 | 56002000 → 12000 |
| 同一物料的连续分配 | 4000 条需求 | 636.5344 / 0.9053 | 614.2045 / 0.5094 | 24002000 → 0 |
| 副产物信用消费 | 1000 种 | 266.7215 / 0.9404 | 212.9407 / 0.6570 | 2502500 → 6000 |

同一键对象命中索引时，连续分配无需逐条调用键的 equals；这就是第二行零次比较的原因。
这些是合成账本场景，耗时受 JIT、GC 和系统负载影响，不能作为真实十亿订单的端到端提速倍数。
